# Knowledge Graph Embedding Theory

## Overview

Knowledge Graph (KG) embeddings are continuous vector representations of entities and relations in a knowledge graph. Instead of operating on discrete graph structures, embedding methods learn to map entities and relations into low-dimensional vector spaces where algebraic operations capture the semantic meaning of relationships.

The core idea: if we can represent the triple `(head, relation, tail)` as vectors, then the plausibility of a triple can be scored by a simple mathematical function over those vectors.

---

## Why KG Embeddings?

Knowledge graphs are inherently sparse. Real-world KGs like Freebase, Wikidata, and YAGO contain millions of entities but only a fraction of all true triples. Embedding methods address this by:

1. **Link prediction**: Inferring missing edges `(h, r, ?)` or `(?, r, t)`
2. **Entity resolution**: Detecting duplicate entities via embedding similarity
3. **Relation extraction**: Discovering implicit relations between entities
4. **Downstream ML**: Using entity vectors as features for classification, clustering, and retrieval

---

## Notation

Throughout this document:

- **h**: head entity embedding vector
- **t**: tail entity embedding vector
- **r**: relation embedding vector
- **E**: set of all entities
- **R**: set of all relations
- **d**: embedding dimensionality
- **S**: set of observed (positive) triples
- **S'**: set of corrupted (negative) triples

---

## TransE: Relations as Translations

### Intuition

TransE (Bordes et al., 2013) is the foundational KG embedding model. The idea is elegantly simple: if `(h, r, t)` is a true triple, then the head entity plus the relation should approximate the tail entity in the embedding space.

```
h + r ~ t
```

Think of it geometrically: the relation vector "translates" the head entity to the tail entity.

### Scoring Function

The plausibility of a triple is measured by how close `h + r` is to `t`:

```
f(h, r, t) = -||h + r - t||_{p}
```

where `||.||_p` is the L1 or L2 norm. Lower distance means more plausible.

### Loss Function (Margin-Based)

TransE uses a margin-based ranking loss to push positive triples closer and negative triples apart:

```
L = sum_{(h,r,t) in S} sum_{(h',r,t') in S'} max(0, gamma + d(h+r, t) - d(h'+r, t'))
```

where:
- `gamma` is the margin hyperparameter
- `S'` is generated by corrupting either head or tail of positive triples
- `d(.)` is L1 or L2 distance

### Negative Sampling

For each positive triple `(h, r, t)`, we create negatives by replacing either `h` or `t`:

```
S'(h,r,t) = {(h', r, t) | h' in E} U {(h, r, t') | t' in E}
```

In practice, we sample a fixed number of negatives per positive (typically 1-50).

### Training Procedure

```
1. Initialize entity embeddings randomly on unit sphere
2. Initialize relation embeddings randomly
3. For each epoch:
     a. Sample a mini-batch of positive triples
     b. Generate negative triples by corruption
     c. Normalize entity embeddings to unit ball
     d. Compute margin-based loss
     e. Update via SGD/Adam
```

### Limitations

- **Cannot model symmetric relations**: If `h + r = t`, then `t + r != h` (unless `r = 0`)
- **Cannot model 1-to-N relations well**: Multiple tails for same `(h, r)` causes embedding collapse
- **Cannot model reflexive relations**: `h + r = h` requires `r = 0`

## RotatE: Relations as Rotations

### Intuition

RotatE (Sun et al., 2019) models relations as rotations in complex vector space. Each entity and relation is embedded in C^d (d-dimensional complex space), and the relation "rotates" the head to the tail:

```
t = h o r
```

where `o` denotes the element-wise (Hadamard) product and `|r_i| = 1` for all dimensions (unit modulus constraint).

### Scoring Function

```
f(h, r, t) = -||h o r - t||
```

Each relation component `r_i = e^{i * theta_i}` is a rotation by angle `theta_i`.

### Why Rotations Work

RotatE can model relation patterns that TransE cannot:

**Symmetric relations** (e.g., "married_to"):
- If `r o r = 1` (rotation by pi), then `h o r = t` implies `t o r = h`

**Antisymmetric relations** (e.g., "parent_of"):
- If `r o r != 1`, the relation is naturally antisymmetric

**Inverse relations** (e.g., "parent_of" / "child_of"):
- `r_2 = r_1^{-1}` (conjugate of rotation)

**Composition relations** (e.g., "grandfather = father o father"):
- `r_3 = r_1 o r_2` (composition of rotations)

### Self-Adversarial Negative Sampling

RotatE introduces a more effective negative sampling strategy. Instead of uniform sampling, it weights negatives by their current score:

```
p(h'_j, r, t'_j) = exp(alpha * f(h'_j, r, t'_j)) / sum_i exp(alpha * f(h'_i, r, t'_i))
```

This focuses training on hard negatives that the model currently scores incorrectly.

## ComplEx: Complex-Valued Embeddings

### Intuition

ComplEx (Trouillon et al., 2016) uses complex-valued embeddings to handle asymmetric relations. The key insight: the Hermitian (conjugate transpose) product in complex space is inherently asymmetric, making it natural for directed relations.

### Scoring Function

Entities and relations are embedded in C^d. The score uses a trilinear product:

```
f(h, r, t) = Re(sum_k h_k * r_k * conjugate(t_k))
```

where `Re(.)` is the real part and `conjugate(.)` is complex conjugation.

### Why ComplEx Handles Asymmetry

The conjugation of the tail creates asymmetry:

```
f(h, r, t) != f(t, r, h)   (in general)
```

This is because `conjugate(h) != h` for complex vectors with nonzero imaginary parts.

### Relation to DistMult

ComplEx is a generalization of DistMult to complex space. When all imaginary parts are zero, ComplEx reduces to DistMult.

---

## DistMult: Bilinear Diagonal Model

### Intuition

DistMult (Yang et al., 2014) is one of the simplest embedding models. It uses a bilinear scoring function with a diagonal relation matrix:

```
f(h, r, t) = sum_k h_k * r_k * t_k = h^T diag(r) t
```

This is equivalent to a weighted dot product between head and tail, where the weights are determined by the relation.

### Strengths

- Extremely fast to compute (element-wise multiplication + sum)
- Works surprisingly well on many benchmarks
- Easy to implement and scale

### Critical Limitation: Symmetry

The scoring function is symmetric:

```
f(h, r, t) = h^T diag(r) t = t^T diag(r) h = f(t, r, h)
```

This means DistMult cannot distinguish `(h, r, t)` from `(t, r, h)`. It works well only for symmetric relations (e.g., "similar_to", "married_to") but fails for asymmetric relations (e.g., "parent_of", "works_for").

## Comparison of Methods

### Scoring Functions Summary

| Method   | Scoring Function                        | Space        |
|----------|-----------------------------------------|--------------|
| TransE   | `-\|\|h + r - t\|\|`                   | Real         |
| RotatE   | `-\|\|h o r - t\|\|`                   | Complex      |
| ComplEx  | `Re(sum h_k * r_k * conj(t_k))`        | Complex      |
| DistMult | `sum h_k * r_k * t_k`                  | Real         |

### Relation Pattern Support

| Pattern         | TransE | RotatE | ComplEx | DistMult |
|-----------------|--------|--------|---------|----------|
| Symmetric       | No     | Yes    | Yes     | Yes      |
| Antisymmetric   | Yes    | Yes    | Yes     | No       |
| Inverse         | Yes    | Yes    | Yes     | No       |
| Composition     | Yes    | Yes    | No      | No       |
| 1-to-N          | No     | Yes    | Yes     | Yes      |

### Complexity

| Method   | Entity Params | Relation Params | Scoring Time |
|----------|---------------|-----------------|--------------|
| TransE   | O(d)          | O(d)            | O(d)         |
| RotatE   | O(d)          | O(d)            | O(d)         |
| ComplEx  | O(2d)         | O(2d)           | O(d)         |
| DistMult | O(d)          | O(d)            | O(d)         |

All methods have linear complexity in the embedding dimension, but ComplEx requires twice the parameters due to complex components (real + imaginary).

## Training Details Common to All Methods

### Initialization

- Entity embeddings: Xavier/Glorot uniform initialization
- Relation embeddings: Xavier/Glorot uniform initialization
- Normalization: entities typically constrained to unit ball (TransE) or unconstrained

### Regularization

- **L2 regularization**: `lambda * (||h||^2 + ||r||^2 + ||t||^2)`
- **Dropout**: Applied to embeddings before scoring
- **Label smoothing**: Soft targets instead of 0/1 for BCE loss variants

### Loss Functions

**Margin ranking loss** (TransE):
```
L = max(0, gamma + f_pos - f_neg)
```

**Binary cross-entropy** (ComplEx, DistMult):
```
L = -y * log(sigma(f)) - (1-y) * log(1 - sigma(f))
```

**Self-adversarial negative sampling loss** (RotatE):
```
L = -log sigma(gamma - d(h o r, t)) - sum_i p_i * log sigma(d(h'_i o r, t'_i) - gamma)
```

### Hyperparameters

Typical ranges for good performance:

| Hyperparameter    | Range           |
|-------------------|-----------------|
| Embedding dim     | 100 - 1000      |
| Learning rate     | 1e-4 - 1e-2     |
| Batch size        | 256 - 4096      |
| Margin (gamma)    | 1.0 - 24.0      |
| Negative samples  | 1 - 256         |
| Epochs            | 100 - 1000      |

## Evaluation Protocol

### Filtered Setting

The standard evaluation protocol for KG embeddings uses the "filtered" setting:

1. For each test triple `(h, r, t)`:
   - Replace tail with every entity: `(h, r, e)` for all `e in E`
   - Score all candidate triples
   - Remove scores of other known true triples (filtering)
   - Rank the correct tail entity

2. Repeat by replacing head: `(e, r, t)`

### Metrics

- **MRR (Mean Reciprocal Rank)**: `1/|T| * sum 1/rank_i` -- average of inverse ranks
- **Hits@K**: Fraction of test triples where correct entity is in top K predictions
  - Hits@1: Exact match accuracy
  - Hits@3: Top-3 accuracy
  - Hits@10: Top-10 accuracy

### Standard Benchmarks

| Dataset    | Entities | Relations | Train    | Valid  | Test   |
|------------|----------|-----------|----------|--------|--------|
| FB15k-237  | 14,541   | 237       | 272,115  | 17,535 | 20,466 |
| WN18RR     | 40,943   | 11        | 86,835   | 3,034  | 3,134  |
| YAGO3-10   | 123,182  | 37        | 1,079,040| 5,000  | 5,000  |
| CoDEx-M    | 17,050   | 51        | 185,584  | 10,310 | 10,311 |

## Beyond Pairwise: Higher-Arity Embeddings

Modern extensions handle:

- **Temporal KGs**: TTransE, TNTComplEx add time embeddings `(h, r, t, time)`
- **Hyper-relational KGs**: StarE embeds qualifier pairs alongside main triples
- **Uncertain KGs**: UKGE models triple confidence scores
- **Multi-modal KGs**: Combine text, image, and graph embeddings

---

## Key Takeaways

1. **Start with TransE** for simple experimentation -- it is fast and provides a good baseline
2. **Use RotatE** when you need to handle diverse relation patterns (composition, symmetry)
3. **Use ComplEx** when asymmetric relations dominate your KG
4. **Use DistMult** when your KG is mostly symmetric and you want speed
5. **Always use the filtered evaluation setting** for fair comparison
6. **Embedding dimension matters**: higher dims capture more but risk overfitting on small KGs
